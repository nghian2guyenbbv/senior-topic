CompletableFuture vs Virtual Threads

Understand when to use each concurrency model in modern Java applications.

⚡ TL;DR

🔵 CompletableFuture

A non-blocking, callback-based API introduced in Java 8. You chain operations (thenApply, thenCompose, allOf) to compose async pipelines without blocking OS threads. Powerful, but can become complex and hard to read.

Java 8+ Non-blocking Callback chains Pipeline composition

🟢 Virtual Threads

Lightweight threads managed by the JVM (Project Loom), available as a preview in Java 19-20 and stable in Java 21. Write plain blocking code — the JVM parks the virtual thread under the hood, keeping OS threads free.

Java 21 GA Blocking-friendly Readable code Project Loom
📊 Feature Comparison
Category 🔵 CompletableFuture 🟢 Virtual Threads
Introduced Java 8 (2014) Java 21 GA (2023)
Execution Model Non-blocking callbacks, runs on a thread pool (ForkJoinPool by default) Blocking I/O — JVM parks the virtual thread while OS thread is freed
Code Style Functional chains — can be hard to follow Imperative / sequential — easy to read
Scalability High — avoids thread blocking Very High — millions of virtual threads possible
Debugging Hard — stack traces are fragmented across callbacks Easy — full sequential stack trace
Error Handling Manual — must use .exceptionally() / .handle() Natural — standard try/catch blocks
Parallel execution & combining results Built-in — allOf(), anyOf() Manual — use StructuredTaskScope (preview) or Future
Timeout Support Built-in — .orTimeout(), .completeOnTimeout() Manual — requires try/catch with interruption
Chaining / Pipeline Excellent — thenApply, thenCompose, thenCombine Not built-in — write sequential code instead
Thread Usage Reuses a fixed thread pool; never blocks a thread on I/O Each task gets its own virtual thread (cheap); maps to carrier OS threads
Spring Boot support Full — works in all versions Full — one config line in Spring Boot 3.2+
Learning Curve Steep — requires async mindset Low — write code like synchronous Java
Best For Complex async pipelines, event-driven systems, reactive patterns I/O-heavy services, REST clients, DB queries, simple parallelism
🎯 When to Use Each

🔵 Use CompletableFuture when...

  • 🔗 You need to chain multiple dependent async steps
  • ⚡ You need to run tasks in parallel and combine results (allOf / anyOf)
  • ⏱️ You need built-in timeout handling (orTimeout())
  • 🌊 You're building a reactive / event-driven system
  • 📦 You're on Java 8–20 (no virtual threads available)
  • 🧩 You need fine-grained control over the thread pool

🟢 Use Virtual Threads when...

  • 📖 You want simple, readable, sequential code
  • 🗄️ Your work is mostly I/O (DB, REST calls, file reads)
  • 🚀 You need high throughput without complex async code
  • 🐛 You want easier debugging with full stack traces
  • 🔄 You're migrating legacy blocking code to be scalable
  • ☕ You're on Java 21+ and want the simplest solution
💻 Code Examples
Example: Fetch user data + orders concurrently, then combine results.
🔵 CompletableFuture Java 8+ 
// Non-blocking pipeline approach
CompletableFuture<User> userFuture =
  CompletableFuture.supplyAsync(
    () -> userService.findById(userId)
  );

CompletableFuture<List<Order>> ordersFuture =
  CompletableFuture.supplyAsync(
    () -> orderService.findByUser(userId)
  );

// Combine both results
CompletableFuture<Dashboard> result =
  userFuture.thenCombine(ordersFuture,
    (user, orders) ->
      new Dashboard(user, orders)
  ).orTimeout(5, TimeUnit.SECONDS)
   .exceptionally(ex -> {
     log.error("Failed", ex);
     return Dashboard.empty();
   });

return result.get();
🟢 Virtual Threads Java 21 
// Simple, sequential-looking code
try (var scope =
    new StructuredTaskScope
          .ShutdownOnFailure()) {

  var userTask = scope.fork(
    () -> userService.findById(userId)
  );
  var ordersTask = scope.fork(
    () -> orderService.findByUser(userId)
  );

  scope.join().throwIfFailed();

  return new Dashboard(
    userTask.get(),
    ordersTask.get()
  );
} // scope closed automatically
Example: Simple fire-and-forget task.
🔵 CompletableFuture 
CompletableFuture.runAsync(() -> {
  emailService.send(email);
}).exceptionally(ex -> {
  log.error("Email failed", ex);
  return null;
});
🟢 Virtual Thread 
Thread.ofVirtual().start(() -> {
  try {
    emailService.send(email);
  } catch (Exception ex) {
    log.error("Email failed", ex);
  }
});

🧠 Bottom Line

Virtual Threads do NOT replace CompletableFuture entirely. They solve different problems. Virtual Threads eliminate the need to write async code just to avoid blocking — you can write blocking code and it scales. CompletableFuture is still the right tool for composing pipelines, combining futures, and timeout logic. In Java 21+, prefer Virtual Threads for simplicity and reach for CompletableFuture when you need its compositional power.

🌱 Spring Boot 3.2+ Tip
💡

Enable Virtual Threads with one line in application.yaml

Add spring.threads.virtual.enabled=true to your application.yaml or application.properties. Spring Boot will automatically use a virtual-thread-per-task executor for @Async, Tomcat request threads, and scheduled tasks — no code changes needed.
